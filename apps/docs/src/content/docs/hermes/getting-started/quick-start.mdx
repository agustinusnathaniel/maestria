Once you've installed the plugin, all skills, commands, and hooks are loaded automatically in every Hermes session. Hermes starts with `fein` as its default mode, which describes the full pipeline.

<Aside type="caution" title="Use full mode deliberately">
  Use `/blitz` for small or well-scoped tasks. Use the default mode when the task benefits from
  review and specialist handoffs. Read [the usage decision guide](/core/when-to-use/) before
  choosing a full pipeline, especially with an expensive or slow model.
</Aside>

## Start a Session

Launch Hermes as usual. The plugin wires itself in at startup. It does not require startup probes for external tools.

## Try the Commands

All features are accessible via slash commands:

```bash
/mode        # Show current mode and role
/mode-clear  # Return to neutral routing
/fein        # Full pipeline: explore → design → build → review
/sonar       # Research only: explore → analyze → stop
/blitz       # Fast execution: build directly
/review      # Trigger review of last output
/plan        # Trigger a planning session
```

**Example workflow:**

```
You:          /fein
Hermes:       Mode set to fein
You:          Research the auth patterns in this codebase
Hermes:       [Adventurer explores, Architect designs, Builder route is capability-gated, Reviewer checks]
```

## Modes at a Glance

| Mode    | Pipeline                                          | When to Use                                                                     |
| ------- | ------------------------------------------------- | ------------------------------------------------------------------------------- |
| `fein`  | Full: adventurer → architect → builder → reviewer | Production work, new features, anything that needs review                       |
| `sonar` | Research: read-only adventurer/planner → stop     | Understanding a codebase, exploring options, no creation                        |
| `blitz` | Direct, read/research/LLM-only                    | Explanation and discovery on known territory; code changes route through review |

The mode directive is injected into every message automatically - no manual prompting needed.

## Specialist Roles and Tool Boundaries

The seven specialist names (adventurer, architect, builder, diagnose, planner, reviewer, writer) are methodology **routing roles** that the orchestrator dispatches to. They are not tool-granting identities on Hermes. Trust and tool capability are governed by the role-neutral child trust policy:

| Context                                                                         | Allowed tools                                                                                                                 |
| ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| **Trusted top-level session** (positively identified by native lifecycle state) | Normal direct behavior. In sonar: read/research only. In direct blitz: a literal read/research/LLM allowlist, no code changes |
| **Delegated child** (spawned via `delegate_task`)                               | Fixed read/research/LLM-only policy. Cannot write, execute code, run a shell, delegate, or invoke OpenCode                    |
| **Ambiguous / invalid / ended child**                                           | Fails closed - denied in all modes                                                                                            |

Under this policy:

- Native Hermes child roles are `leaf`/`orchestrator` topology roles only, not Maestria specialist roles.
- User or delegation text cannot grant capabilities; role markers in messages are ignored.
- Review/landing enforcement is advisory (Hermes has no native review-state or landing gate).
- Role-specific delegated builder writes are deferred until Hermes provides an authenticated capability channel.

Direct code changes on Hermes are performed by a trusted top-level session (typically fein), not by a delegated `builder` child.

## Pairing with Platform Features

For multi-turn or long-running work, pair maestria pipelines with Hermes platform features:

| Feature                      | How it helps                                                                                                                                                                       | Links                                                                                                                            |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| **`/goal`**                  | Set a persistent objective (`/goal draft Run the fein pipeline to implement OAuth`). The goal loop survives session boundaries; mode and pipeline state restore on `/goal resume`. | [Docs](https://hermes-agent.nousresearch.com/docs/user-guide/features/goals) · [GitHub](https://github.com/nousresearch/hermes)  |
| **Mnemosyne** (agent memory) | Cross-session agent memory remembers your mode preference, past pipeline context, and working patterns across sessions.                                                            | [Docs](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory) · [GitHub](https://github.com/nousresearch/hermes) |
| **Uteke** (knowledge base)   | Store specialist findings and pipeline decisions as searchable wiki documents for long-term project reference.                                                                     | [Docs](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory) · [GitHub](https://github.com/codecoradev/uteke)   |

Configure Mnemosyne or Uteke in `config.yaml` under `memory:`. See the [Installation Guide](/hermes/getting-started/installation/) for details.
