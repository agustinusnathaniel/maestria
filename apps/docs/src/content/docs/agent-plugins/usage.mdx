---
title: Usage
description: Run maestria workflows, request independent review, and use the skills on any Agent Plugins host.
---

Once [installed](/agent-plugins/installation/), hosts with native support offer the same three workflow modes and one reviewer; Hermes and marketplace-only Codex installs supply only the eight skills. The syntax differs by host; the [per-host table](#per-host-syntax) lists it. For small tasks, read [When to use maestria](/core/when-to-use/) before choosing the full method.

## Run a workflow

Pick a mode and give it a concrete goal:

| Mode | Use |
| --- | --- |
| `fein` | Full method: `recon` and `architecture-plan` skills, implementation in the main loop, and required blind review |
| `sonar` | Research only in the main loop, then stop before implementation; change no files and dispatch no subagents |
| `blitz` | Smallest safe route for familiar work, keeping verification and required review |

Each command or keyword carries the complete routing, mode instructions, and global policy, so no skill preload is needed and your task arguments are preserved. For example, on Claude Code:

```text
/maestria:fein Add rate limiting to the API.
```

On Codex, which has no plugin slash commands, the same mode is a keyword such as `FEIN: <goal>`. On Devin the modes are skills: `/maestria:fein <goal>` in the CLI or Desktop, or `@skills:fein <goal>` in the web app. See the table below.

## Request independent review

The reviewer is the only specialist. Ask the host's main agent to send a meaningful change to it, naming a concrete outcome, the file scope, constraints, and acceptance evidence:

```text
With the recon skill, trace authentication in src/auth/.
Return the relevant files, call paths, and uncertainties without editing.
```

The reviewer profile embeds its complete role and the global policy, so the child does not depend on the parent loading any skill. Delivery ownership (workflow modes, autonomous commit, push, and PR, and PR slicing) stays with the main session's routing context, so a review brief does not carry it. Pass the task details in the brief, not the methodology.

Keep maker and checker separate. After implementation, dispatch `reviewer` on its own; never ask the agent that made a change to approve it. For example, ask for a bug to be traced, fixed, and reviewed: trace it in the main loop with the `recon` skill, loading `diagnose` for an unknown cause, apply the minimal fix, then have a separate `reviewer` validate it. For a small local fix, load the `diagnose` skill directly in the main loop.

## Read-only review

`reviewer` is meant to review without editing; the main loop researches and designs with the `recon` and `architecture-plan` skills. How strongly the read-only boundary holds depends on the host:

| Enforcement | Hosts |
| --- | --- |
| Write and Edit tools removed or denied | Claude Code, Kimi Code, ZCode (shell stays available) |
| Declared but not enforced for plugin agents | Cursor (enforced for project `.cursor/agents/` copies written by `maestria configure cursor`) |
| Prompt-level only | Codex (it no longer applies a role's `sandbox_mode`), Devin, OMP |

None of these is a shell sandbox, and the host keeps control of permissions. See [compatibility](/agent-plugins/compatibility/) for the evidence behind each row.

## Skills

Eight skills work on every host: `handoff` briefs a delegate, retries a failed delegation, and tracks work across sessions; `review-loop` briefs the reviewer, triages its findings, and bounds repair passes; `implement` holds implementation judgment, behavior-level testing, and comment rules; `create-pull-request` drafts PR titles and bodies; `docs-update` keeps docs and changesets in step with a change; `diagnose` traces a failure to its root cause; `recon` maps unfamiliar code; and `architecture-plan` compares approaches and writes a phased plan. They guide the agent and do not restrict tools. They are not specialists or workflow commands; loading them registers no agents and activates no routing.

```text
Use the handoff utility to summarize this task's outcome, constraints,
evidence, blockers, and next step.
```

## Hooks

On hosts that run plugin hooks, maestria adds small Node scripts that back up rules the directives already state. They need `node` on `PATH`; a hook that cannot run does nothing, and the rules still apply.

| Job | What it does | Hosts |
| --- | --- | --- |
| Always-on core | Adds the main loop and global rules at session start, after `/clear`, and after compaction | Claude Code, ZCode |
| Project customization | Adds project-root `.maestria/workflow.md` then `.maestria/rules.md` at session start | Claude Code, ZCode, Codex, Cursor, Devin |
| Git safety | Blocks `--no-verify` and a one-off `git -c core.hooksPath=...` on commit or push; asks before commits or pushes to `main`, `develop`, `staging`, or `release/*`, force pushes, `git reset --hard`, `git clean -f`, `git checkout -- <path>`, `git restore <path>`, and `git stash drop` | Claude Code, ZCode, Codex, Cursor, Devin, Kimi Code |
| Generated-file guard | Asks before an edit tool changes a file marked `@generated`, `DO NOT EDIT`, `Do not edit directly`, or `Generated by/from` near its top | Claude Code, ZCode, Codex, Cursor, Devin, Kimi Code |
| Email scan | Asks before PR, issue, API, or commit text that contains an email address (noreply addresses excepted) | Claude Code, ZCode, Codex, Cursor, Devin, Kimi Code |

Claude Code, ZCode, and Cursor's shell hook can ask you to confirm. Codex, Kimi Code, Devin, and Cursor's file-edit hook cannot ask, so they block and tell the agent to get your approval first. Codex runs the hooks only after you trust them with `/hooks`, and asks again after each plugin update; Devin and Kimi Code skip a hook that fails. Edits to `.maestria/` files apply after `/clear` or compaction (OpenCode and Pi re-read them every turn).

To turn the hooks off, use your host's own settings for plugin hooks, or leave them untrusted on Codex; disabling the plugin also stops them. maestria has no separate switch.

## Per-host syntax

| Host | Run a mode | Request review | Skills |
| --- | --- | --- | --- |
| Claude Code | `/maestria:fein <goal>`, `/maestria:sonar <goal>`, `/maestria:blitz <goal>` | Agent tool identity `maestria:reviewer` for independent review | `maestria:<skill>`, for example `maestria:handoff` |
| Codex | Keywords `FEIN:`, `SONAR:`, `BLITZ:` (case-insensitive, per turn) or a marker such as `[MODE: sonar]`; needs the companion CLI install | `agent_type: "maestria-reviewer"` for independent review | `$maestria:<skill>`, for example `$maestria:handoff` |
| Cursor | `/fein <goal>`, `/sonar <goal>`, `/blitz <goal>` in Agent chat (IDE or CLI) | Ask Agent chat to send the change to the reviewer; it runs as a Task agent | The eight skills by name, for example `handoff` |
| Kimi Code | Choose `fein`, `sonar`, or `blitz` from the command picker and add the task | Ask for the reviewer plugin agent | The eight skills by name, for example `handoff` |
| Devin | `/maestria:fein <goal>` and the other mode skills in the CLI or Desktop, `@skills:fein <goal>` in the web app; there are no plugin commands | Devin's reviewer subagent controls in local CLI and Desktop sessions only | The eight skills by name, for example `handoff` |
| ZCode | Choose the fein, sonar, or blitz command from the prompt picker | Native subagent controls with a complete review handoff | The eight skills in the Skills group |
| OMP | `/fein <goal>`, `/sonar <goal>`, `/blitz <goal>` | Native `task(agent, task)` with `reviewer` as the agent | The eight skills by name, for example `handoff` |
| Hermes | None; manual context only | Delegate the review manually and pass the reviewer guidance, policy, and constraints to the child | Qualified names from `skills_list`, loaded with `skill_view` |

A few host details are worth knowing:

- **Codex.** The modes are instruction entry points from the managed routing block, not installed skills or slash commands. Codex no longer applies a role file's `sandbox_mode`, so the reviewer's read-only role is prompt-level. A marketplace-only install has the utilities but no modes or reviewer.
- **Cursor.** Profiles and commands embed their full methodology, and the always-apply rule supplies routing. Direct execution or the reviewer alone is often better for small changes and expensive models.
- **Kimi Code.** Kimi chooses the model because plugin profiles have no per-agent model field.
- **Devin.** Root `AGENTS.md` carries the routing and policy within Devin's 16 KiB always-on cap, and the modes ship as skills. Cloud sessions can use the skills and policy but not plugin subagents.
- **OMP.** Profiles inherit the parent model by default, and the package adds no persistent mode mechanism or session interception.
- **Hermes.** Portable skill names depend on the Hermes version (`<plugin>:<skill>` from v0.22.6, `agent-plugin-<slug>-<hash>:<skill>` before), so discover them with `skills_list`. Native agent registration and delegation remain Hermes capabilities. To add routing and mode guidance, follow the [manual context setup](/agent-plugins/installation/#hermes-manual-context).
- **Claude Code.** Commands and utilities can load in Claude Chat, but the full workflow needs delegation, which Chat lacks. See [Claude Chat and Cowork](/agent-plugins/installation/#claude-chat-and-cowork).
