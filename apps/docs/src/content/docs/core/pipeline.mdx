When a task needs more than direct execution, the main loop works through it in stages. It selects the method skills that add information or reduce risk; it does not load every skill for every task.

## The Three Concerns

| Stage | Question | How | Output |
| --- | --- | --- | --- |
| Understand | What do we know, and what should we do? | `recon`, `architecture-plan`, or `diagnose` in the main loop | Reconnaissance, a decision, a phased plan, or a confirmed cause |
| Make | Can we produce the requested result? | Implementation in the main loop | The implementation or documentation change |
| Check | Does the result meet the evidence and quality requirements? | reviewer | An independent review with actionable findings |

The main loop handles understand and make itself (loading `diagnose` when the cause is not established); reviewer inspects without editing. The separation keeps one agent from approving its own work.

## Flow

The common route, with each skill optional:

```text
main loop with `recon` / `architecture-plan` / `diagnose` when needed
    -> implementation in the main loop
    -> reviewer when independent validation is required
```

Each review brief carries the outcome, context and constraints, acceptance evidence, and next step; link to existing artifacts instead of copying the conversation.

Adapt the route to the task:

- Load `recon` when the code or dependency path is unfamiliar, or when the affected surface is unclear.
- Load `architecture-plan` when the approach has meaningful trade-offs, or when delivery needs milestones, verification criteria, or rollback points.
- Load `diagnose` for a bug, regression, failure, or crash with an unknown cause.
- Skip a skill when the task is familiar and already scoped, or stop after research for research-only requests.

If reviewer rejects the result, repair an implementation defect in the main loop and reshape a design or scope defect with `architecture-plan`. Do not guess at a rejected design.

## Maker/Checker Split

The main loop that produces an artifact must not be the one that validates it. This is the workflow's core quality boundary.

<Aside type="caution" title="Reviewer independence">
  A reviewer may need context from the main loop, but it must inspect the maker's result
  independently and report findings without editing it.
</Aside>

Use one independent reviewer for ordinary work; add a security, architecture, performance, or UX lens only when the requirements or diff expose that risk. See [Workflow Patterns](/core/workflow-patterns/) for practical review routes.

## Bound the Repair Loop

Define a verifiable stopping condition before delegating. When review finds blockers, one repair/re-review pass is the default; another only when a named blocker remains unresolved or the repair introduces a new material regression, capped at three per outcome. If the same cause recurs, escalate with:

```text
Tried X, Y, Z. Blocked by [cause]. Need [input] to proceed.
```
