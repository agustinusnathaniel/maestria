Maestria adds structure through delegation, handoffs, and review. That structure costs model work, context transfer, and waiting time. Use it when the extra information or independent check is worth the cost.

## Quick Decision

| Situation | Start with | Why |
| --- | --- | --- |
| One or two known files and an obvious change | Direct execution | Delegation adds coordination without much new information |
| Small bug in unfamiliar code | adventurer or diagnose | Recover the missing context before changing files |
| UI, copy, or interactive iteration | Direct execution or blitz | Short feedback loops matter more than formal handoffs |
| Shared workflow across compatible clients | [Portable Agent Plugin](/agent-plugin/) | Share skills while the client owns activation and permissions |
| Multi-file work in an unfamiliar codebase | Orchestrator or fein | Reconnaissance and staged review reduce rework |
| Security, migration, or other high-risk work | Full pipeline with review | Independent validation justifies the overhead |
| Research or feasibility question | sonar | Stop after analysis instead of creating implementation work |

## Choose the Route

| Turn | Default route | Escalate when |
| --- | --- | --- |
| Explanation or discovery | Direct answer or one focused specialist | The answer depends on several modules or a consequential decision |
| Tiny edit | Direct execution | It touches behavior, generated files, or a security-sensitive boundary |
| Ordinary code change | Direct implementation plus focused review | The change spans packages or has unclear requirements |
| Complex or high-risk change | Full pipeline | New evidence exposes design, security, or operational risk |

The mode names vary by platform, but the trade-off is the same:

- fein selects the full pipeline.
- sonar stops after research or design.
- blitz keeps only the required safeguards and validation around a fast implementation path.

<Aside type="caution" title="Full pipeline is an explicit trade-off">
  Do not choose the full pipeline only because a task has several steps. Choose it when separate
  stages add information, reduce risk, or create an independent check.
</Aside>

## Three Ways to Work

### Direct Execution

Use the platform's normal agent when the task is familiar, small, or easy to verify. This is often the fastest and cheapest path.

### Specialist Delegation

Use one specialist when you need one kind of help:

- adventurer maps unfamiliar code.
- architect compares approaches.
- diagnose traces a failure.
- planner creates phased milestones.
- reviewer checks a result independently.
- writer produces structured documentation.

Combine that result with direct implementation when a full pipeline would add little value.

### Full Orchestration

Use the orchestrator for cross-module features, risky changes, unfamiliar systems, or work that needs a durable handoff across sessions. The [Pipeline & Roles](/core/pipeline/) page explains the stages.

## Model and Platform Costs

Each delegated stage can add:

- another model turn and its prompt tokens
- context transfer and cache reads
- waiting before the next dependent stage
- more repair work if review finds a problem

Strong or expensive models often make direct execution or one specialist the better choice. Fast, inexpensive models can make narrow delegation a reasonable trade. Start with the smallest route and escalate when uncertainty or risk appears.

Platform behavior also changes the trade-off:

- OpenCode and Claude Code provide the strongest package-level tool boundaries described by their guides.
- Codex CLI, Cursor, and Prime Agent rely more on host controls and advisory methodology boundaries.
- Kimi Code applies permission rules to the session; Pi and OMP differ in dispatch and context inheritance; Hermes uses role-neutral child trust.
- The portable Agent Plugin provides skills, while the consuming client owns discovery, activation, permissions, and session behavior.

Read the platform guide before assuming that a route, permission, or lifecycle behavior transfers unchanged.

## Examples

| Request                                  | Good starting point           |
| ---------------------------------------- | ----------------------------- |
| Add a JSDoc comment to a known function  | Direct execution              |
| Find where authentication tokens refresh | adventurer                    |
| Trace an intermittent login failure      | diagnose                      |
| Migrate authentication across packages   | Full pipeline or fein         |
| Review changed files for security issues | reviewer with a security lens |

<Aside type="tip" title="A practical rule">
  If the task is one atomic edit, start directly. If a wrong assumption is expensive, add a
  specialist or independent review.
</Aside>
