## Match the Task to a Route

| Task | Start with | Continue with |
| --- | --- | --- |
| Familiar, atomic change | Direct execution in the main loop | Review only if the risk warrants it |
| Unfamiliar codebase or dependency path | `recon` in the main loop | Implement directly |
| Consequential choice or phased plan | `architecture-plan` in the main loop | Record the decision, then implement |
| Multi-step feature or migration | `architecture-plan` with milestones | Implement each atomic milestone, then reviewer |
| Bug with an unclear cause | `diagnose` in the main loop | Implement the confirmed fix, then review |
| Documentation or release notes | Implement in the main loop | Review the rendered or published result |
| Pre-merge validation | reviewer | Fix findings, then rerun the relevant checks |
| Complex or high-risk change | Full-method mode | Stop when reviewer accepts the result |

Add a skill or review only when it supplies missing information, reduces a material risk, or creates a useful independent check.

## Keep Review Briefs Small

Give reviewer enough to act without copying the whole conversation:

```text
Outcome: what the recipient must produce
Context and constraints: relevant files, decisions, and limits
Acceptance/evidence: how to tell the result is complete
Next step: who consumes the result
```

Prefer links to existing artifacts, omit empty fields, and keep the brief proportional to the task. For example:

> Reviewer: Review the accepted session-refresh design as implemented at the given commit or branch; acceptance is the stated criteria; binding constraints are those in the brief. Verify the diff independently. Do not edit.

> Main loop: Implement the accepted session-refresh design as one atomic change; run the focused tests and report changed files, evidence, and unresolved assumptions. Reviewer receives the result.

## Common Sequences

- **Understand, then implement** - `recon in the main loop -> direct implementation -> reviewer when needed`. Stop reconnaissance once the entry points, dependencies, and constraints are known.
- **Decide, then implement** - `architecture-plan in the main loop -> implementation -> reviewer`. Write a phased plan when delivery needs ordered milestones, verification criteria, or rollback points.
- **Diagnose, then fix** - `diagnose in the main loop -> implementation -> reviewer`. Hand over the confirmed cause, affected paths, smallest safe fix, and prevention evidence.
- **Research only** - `recon with architecture-plan when the request is a design or plan -> stop`. The research-only mode packages this boundary where the platform supports it; a research result states what was learned, what remains uncertain, and what would justify implementation. Change no files and dispatch no subagents.

## Match review depth to risk

Use one independent reviewer for ordinary pre-merge validation, adding a security, architecture, performance, or UX lens only when the requirements or diff expose that risk. The main loop must not review its own artifact; [Pipeline & Roles](/core/pipeline/) covers repair-loop limits.

## Project-Specific Workflows

Projects may add two root-only files, loaded in order: `.maestria/workflow.md` for project context, required reading, and quality gates, then `.maestria/rules.md` for local non-negotiable constraints. Each file carries a subordinate-guidance header: it may replace configurable workflows but never waives safety, authorization, or host permissions. Runtime safeguards, selected-route protections, review independence, bounded retries, and commit authorization still take precedence.

Keep these files short: reusable methodology belongs in the canonical maestria directives, project decisions in ADRs, and one-off task details in the handoff.

### How engines load them

| Engine | Project root | Freshness |
| --- | --- | --- |
| OpenCode | Project directory, or the session directory when OpenCode reports no project | Read fresh for every agent-loop and compaction request; edits need no restart |
| Pi | Session working directory, each turn | Read fresh on every agent turn, composed with the mode prompt |

Compaction and carry-over preserve them: OpenCode sends the current project constraints and rules with every agent-loop and compaction request; Pi recomposes sections each turn and persists the mode across turns in the same process.

The declarative Agent Plugins integrations provide instructions to read project guidance; they do not install this runtime loader or its freshness and compaction guarantees. OMP owns native rule discovery, and Hermes requires optional manual host context configuration.

### Absent versus unusable

Missing or empty files are skipped silently. A present-but-unusable file (a directory, a non-file, a symlink escaping the project root, or an unreadable file) fails loud with a diagnostic that names only the relative path, never absolute paths or file contents. OpenCode fails the request while assembling its context; Pi surfaces it via notification plus a STOP banner. Do not execute the request until the files are fixed.
