Maestria applies **Harness Engineering**: the model supplies capability, while the harness supplies the method that makes work repeatable. In Maestria, the harness is a dispatcher, a set of specialist roles, explicit handoffs, and independent verification.

The short version is:

```text
request -> route -> focused work -> evidence -> result
```

The [Pipeline & Roles](/core/pipeline/) page describes the mechanics. This page explains the intended benefits and their limits.

## The Core Model

The orchestrator decides which work is needed and delegates it to one or more of the 7 specialists. A specialist returns a focused artifact: reconnaissance, a decision, a plan, an implementation, a diagnosis, a review, or documentation.

| Boundary             | Purpose                                                              |
| -------------------- | -------------------------------------------------------------------- |
| Focused specialist   | Keeps one concern and its evidence in view                           |
| Handoff              | Carries the context, constraints, acceptance evidence, and next step |
| Stage gate           | Stops the workflow when the output is incomplete or unsafe           |
| Independent reviewer | Checks the maker's result without editing it                         |

Direct execution remains valid for small, familiar work. Delegation earns its cost only when it adds information, reduces risk, or provides an independent check.

## Designed Benefits

| Benefit | How the harness provides it |
| --- | --- |
| Focus | Specialists receive a narrow responsibility instead of one prompt that mixes discovery, design, implementation, and review. |
| Earlier correction | Thinkers can expose missing context or a bad approach before a worker spends time implementing it. |
| Independent validation | The reviewer is a separate role with read-only responsibilities and different incentives from the maker. |
| Bounded failure | Repair loops use a verifiable stopping condition, normally allow about three attempts, and escalate when progress stops. |
| Consistent expectations | Global rules define evidence, authorization, escalation, and commit behavior across the native integrations. |

These are design goals, not guarantees. Quality still depends on the task, model, host runtime, and quality of the evidence produced.

<Aside type="caution" title="The pipeline has a cost">
  Every delegated stage adds model work, context transfer, and waiting time. Use the [usage decision
  guide](/core/when-to-use/) to decide whether that cost is justified.
</Aside>

## A Typical Full Route

```text
orchestrator
    -> thinker: adventurer, architect, planner, or diagnose
    -> worker: builder or writer
    -> verifier: reviewer
```

The route is adaptive. A small change may go directly to a worker. A bug may start with diagnose. A design uncertainty may require architect before builder. A research-only request stops after the thinker stage.

The verifier accepts the result only when the stated acceptance evidence is present. If it finds an implementation defect, the worker repairs it. If it finds a design defect, the orchestrator returns to the thinker instead of asking the worker to guess.

## What Depends on the Platform

Native integrations can provide stronger runtime boundaries, such as read-only permissions, lifecycle hooks, or native subagents. The [Agent Plugin package](/agent-plugin/) provides the skills and contracts, while the consuming client owns discovery, permissions, activation, and session behavior.

Platform behavior also differs in context inheritance and parallel dispatch. A new specialist session may still inherit part of its parent's context, so treat the handoff as the reliable boundary rather than assuming isolation.

Read the relevant platform guide before relying on a permission or lifecycle claim. The core methodology describes the intended contract; each adapter documents what its host can actually enforce.

## What It Does Not Promise

- It does not make every task faster than direct execution.
- It does not replace the host's sandbox, permission system, or model configuration.
- It does not make advisory rules into security controls.
- It does not remove the need for tests, evidence, or human judgment on consequential work.
