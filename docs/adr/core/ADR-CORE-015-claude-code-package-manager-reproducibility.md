# ADR-CORE-015: Claude Code Package Manager Reproducibility

## Status

Proposed (2026-08-12). This ADR records a workspace-level package manager policy decision made to land the `@maestria/claude-code` plugin package reproducibly. It accompanies the runtime decision boundary in [ADR-CORE-014](ADR-CORE-014-runtime-support-and-adapter-policy.md) and the evidence ledger in [runtime-support-matrix.md](../../runtime-support-matrix.md).

## Context

The first implementation batch for the Claude Code adapter (ADR-CORE-014, `Native candidate`, plugin delivery) produced a declarative plugin package in `packages/claude-code/`: generated agents, skills, and commands from the core sync pipeline (ADR-CORE-005), a local `tsx`-based sync script, tests, manifest, and a changeset. The package is validated locally with `claude plugin validate --strict` and runs its test suite through the shared Vite toolchain (`vite-plus` / `vitest` from the workspace catalog).

While landing that package, the workspace toolchain pinning surfaced a reproducibility problem. The shared catalog entries for the Vite toolchain were declared as floating ranges:

```yaml
vite: npm:@voidzero-dev/vite-plus-core@latest
vite-plus: latest
```

The committed `pnpm-lock.yaml` resolved those entries to `vite-plus@0.2.7` at the time it was generated, so the repo was internally consistent. But any lockfile regeneration (for example adding the missing `packages/claude-code` importer to the lockfile) re-resolved `latest` against the registry and drifted the entire shared toolchain: controlled pnpm experiments resolved `latest` to `0.2.8` (with `@voidzero-dev/vite-plus-core@0.2.8`, `oxfmt@0.61.0`, `oxlint@1.76.0`) and, once `0.2.9` became available, to `0.2.9` (with `oxfmt@0.62.0`, `oxlint@1.77.0`). Because `vite`, `vite-plus`, `vitest`, and the Oxc formatter/linter are shared by every package in the workspace through the catalog and overrides, this drift was not local to the Claude package - it touched the docs app, the CLI, and every plugin package in one lockfile regeneration.

The Claude package does not depend on any specific newer toolchain version. It needs the shared toolchain to be present, consistent, and reproducible. The drift therefore had no functional benefit for this batch and only added unrelated lockfile churn plus risk of untested toolchain changes landing inside a policy-focused change.

### Authorization

The user explicitly authorized (2026-08-12, on branch `feat/runtime-support-adapters`) changing the existing `vite` and `vite-plus` catalog entries from `latest` to the exact `0.2.7` versions, and the generated `pnpm-lock.yaml` importer and dependency updates for `@maestria/claude-code`. The authorization is limited to this pin and the Claude package's lockfile importer; it does not authorize a `0.2.8` (or newer) upgrade, any other catalog changes, hooks, MCP, CLI handlers, model registry, or other runtime work.

## Decision

Pin the shared Vite toolchain catalog entries to the exact versions that the committed lockfile already resolved:

```yaml
vite: npm:@voidzero-dev/vite-plus-core@0.2.7
vite-plus: 0.2.7
```

All other catalog entries, overrides, peer dependency rules, and allow-build settings remain unchanged. The `pnpm-lock.yaml` is regenerated by pnpm (never hand-edited) and gains the `packages/claude-code` importer plus the required transitive entries; the regeneration is audited to contain no `vite-plus`/Oxc `0.2.8` (or newer) drift and no unrelated catalog changes.

Future Vite toolchain upgrades are separate, intentional policy changes: a maintainer decides to move the whole workspace to a newer `vite-plus`, makes that a deliberate catalog change, and regenerates the lockfile under review - never an incidental side effect of adding a package importer.

## Consequences

### Positive

- Adding a package importer to the lockfile no longer silently upgrades the shared Vite/Oxc toolchain. Lockfile regeneration is reproducible: the pinned catalog entries resolve to exactly the versions the lockfile records.
- The `@maestria/claude-code` importer lands in the lockfile without unrelated toolchain churn, keeping the diff auditable.
- All workspace packages keep using the same toolchain version (`vite-plus@0.2.7`, `@voidzero-dev/vite-plus-core@0.2.7`), so the shared toolchain remains consistent across docs, CLI, and plugins.
- The committed lockfile's resolved versions match the catalog pins, so `pnpm install --frozen-lockfile` is stable and CI does not depend on `latest` resolution timing.

### Negative

- The workspace no longer automatically receives `vite-plus` patch/minor updates when they are published; upgrades require an explicit policy change. This is intended: toolchain upgrades become deliberate, reviewed decisions rather than lockfile side effects.
- `vite-plus` and `vite` catalog entries are now pinned exact versions while most other catalog entries use ranges, which is a small consistency divergence in the catalog. It is justified by the reproducibility requirement and documented here.

Lockfile regeneration also refreshed compatible transitive picomatch edges from 4.0.4 to 4.0.5, while retaining 4.0.4 for dependency edges that still resolve it. This is generated pnpm lockfile output, not a direct dependency change or a Vite+ upgrade, and was audited as part of importer regeneration.

## Alternatives Considered

### Option A: Keep `latest` and accept the drift

Rejected. Every lockfile regeneration would re-resolve the shared toolchain against the registry (`0.2.8` at experiment time, `0.2.9` later), pulling new Oxc formatter/linter versions into the docs app, the CLI, and every plugin package. That is unrelated scope for a package-landing change and makes the lockfile diff non-deterministic over time. The committed lockfile would also no longer match a fresh `pnpm install`, breaking frozen-lockfile reproducibility.

### Option B: Pin only `vite-plus`, leave `vite` at `latest`

Rejected. `vite` is the same toolchain as `vite-plus` (the catalog entry is an alias to `@voidzero-dev/vite-plus-core`). Leaving `vite` floating while pinning `vite-plus` would still re-resolve the core package on regeneration and recreate the drift through the override chain (`vite: 'catalog:'`). Both entries must move together.

### Option C: Upgrade the whole workspace to `0.2.8` (or newer)

Rejected as out of scope. The user authorized the `0.2.7` pin and the Claude importer only, not a toolchain upgrade. A workspace-wide `vite-plus` upgrade is a separate, intentional policy change that deserves its own review and validation, not a side effect of landing a package.

## Rollback

To revert this decision:

1. Restore the catalog entries in `pnpm-workspace.yaml` to `vite: npm:@voidzero-dev/vite-plus-core@latest` and `vite-plus: latest`.
2. Regenerate the lockfile with `pnpm install --lockfile-only` (or revert `pnpm-lock.yaml` to the previous committed version and re-add the Claude importer via pnpm).
3. Re-verify with `pnpm install --frozen-lockfile`, the package test suites, `pnpm check`, and `scripts/check-sync` before committing the revert.

Rolling back the pin does not remove the `@maestria/claude-code` package or its importer; it only restores floating toolchain resolution (with its reproducibility caveats).
