# ADR-CORE-018: Documentation Standard and Content Catch-up

## Status

Accepted (2026-08-13)

## Context

The multi-package, multi-platform monorepo had uneven documentation: internal guidance covered only the ADR template; publishable READMEs used unrelated structures; the public Astro/Starlight docs site lacked a user-facing section for `@maestria/prime-agent`; and public changelog pages lagged released artifacts.

As a result:

- Contributors had to read examples to learn what sections a plan, note, or guide requires.
- Consumers could not reliably find a package's support boundary, limitations, or development workflow.
- New packages had no user-facing docs until someone remembered to add them, with no checklist for the index, getting-started, changelog, and contributing pages.
- The docs sidebar and LLM description omitted Prime Agent, and changelog pages referenced outdated or upcoming versions.

## Goals

1. Make the internal documentation rules explicit in `docs/guides/doc-format.md`: required sections per document type, the internal-vs-public distinction, and `[verified]`/`[inferred]` evidence tagging.
2. Record this documentation standard as an ADR so the decision is auditable.
3. Add a user-facing docs section for `@maestria/prime-agent` (overview, installation, quick start, changelog, contributing) following existing Starlight conventions and preserving the package's verified-subset/support boundary.
4. Include Prime Agent in the docs sidebar and LLM description.
5. Catch up the public changelog pages so each currently released artifact is represented as a curated summary, using observed versions rather than invented release claims.
6. Standardize the publishable package READMEs onto a consistent, useful section order while preserving package-specific facts and commands.
7. Update the root `README.md` uninstall links and `CONTRIBUTING.md` stale package/version references.
8. Validate docs-related changes through the docs-site deployment build, which runs on every preview and covers docs-only changes skipped by CI path filters.

## Non-Goals

- No changes to package source code, sync pipeline, generated projections, lockfiles, or existing CI workflows. No dedicated GitHub Actions docs-site workflow is added: deployment previews are the docs validation path, and existing workflow files and path filters are left unchanged.
- No edits to any package `CHANGELOG.md`; the public changelog pages are curated summaries, not generated copies.
- No retrofitting of every legacy internal document; the standard applies to new and materially revised documents only.
- No programmatic enforcement of the documentation format (no new lint rules or format-validation CI checks). The docs-site deployment build validates that the site builds and links resolve; it is not a format gate.
- No new package release claims or invented versions; changelog and README content reflect observed manifests.

## Decision

1. **Expand `docs/guides/doc-format.md`** into the internal documentation standard: required sections per document type (ADR, plan, notes/guides), `[verified]`/`[inferred]` tagging, separation of internal rationale from public usage, and no retrofitting of legacy docs.
2. **Record the decision** in this ADR, following the existing ADR numbering and format.
3. **Add a Prime Agent docs section** (overview, installation, quick start, changelog, contributing) mirroring comparable packages, stating its `Native candidate` status, verified skills plus extension subset, and deferred items (`rlm` dispatch, JSON/RPC headless mode) without claiming unsupported runtime enforcement.
4. **Update the docs site config** to add a `@maestria/prime-agent` sidebar group and include Prime Agent in the LLM description.
5. **Catch up the public changelog pages** so each currently released artifact is represented as a curated summary with a consistent current/date heading, without inventing package release claims.
6. **Standardize the publishable package READMEs** onto the mandatory section order: Motivation, Goals, Non-Goals, Status / Support Boundary, Installation or Usage, What It Provides, Limitations / Platform Notes, Development, Documentation and Changelog, License. Each keeps package-specific details and commands, links public docs and package changelogs where they exist, links `INSTALL.md` where shipped, and mentions canonical core directives for generated plugin packages. Versions are avoided in README prose except for support boundaries.
7. **Update the root `README.md`** to add uninstall links for all published platform packages, and **update `CONTRIBUTING.md`** to fix stale package/version references and its docs/package contract/sidebar description, keeping the sidebar description accurate (manual-plus-autogenerated, not fully auto-generated).
8. **Rely on deployment preview builds for docs validation** instead of a dedicated GitHub Actions workflow. The site deploys to Cloudflare Pages: production on `main` pushes and a preview deployment on every PR, not path-filtered, so docs-only PRs skipped by CI path filters still get a preview build. The deployment build runs the Starlight build including link checking; `astro build` runs content-collection sync internally, so the separate docs sync step is a type-generation convenience, not required validation. No separate docs workflow is maintained, and repository-docs-only changes still trigger a preview build even though they do not affect the site; that cost is accepted.

## Consequences

### Positive

- Contributors get an explicit, discoverable documentation standard instead of inferring structure from examples.
- Consumers of every published package can find the same sections (motivation, support boundary, usage, limitations, development, license) regardless of platform.
- New packages have a defined docs contract, so Prime Agent ships complete user-facing documentation.
- The docs site and public changelogs reflect current releases, reducing "which version is current" confusion.
- Root README and CONTRIBUTING no longer point at outdated versions or omit platforms.
- Docs-related changes are validated by the docs-site deployment build on every preview and production deploy instead of silently bypassing CI; CI path filters are untouched and no separate docs workflow is maintained.

### Negative

- The README standardization rewrites many files, risking the loss of package-specific nuance if not done carefully (mitigated by preserving each package's truthful details and commands).
- Standardizing changelogs as curated summaries means the public pages can drift from the package `CHANGELOG.md` if not kept in sync during each release.
- The documentation standard adds a section checklist to new internal documents, increasing authoring overhead (consistent with the existing ADR overhead trade-off).
- Docs validation depends on the Cloudflare Pages pipeline: the build command must keep running the docs build, and repository-docs-only changes still incur a preview build (accepted to avoid docs-only PRs running no checks at all).

## Assumptions

- The package manifests reflect the released versions; the changelog pages use those observed versions rather than inventing release claims. `[verified]`
- The docs site uses `starlight-auto-sidebar` plus an explicit sidebar config; the sidebar and LLM description are manual-plus-autogenerated, not fully auto-generated. `[verified]`
- Packages that ship an `INSTALL.md` are linked from their READMEs; packages without one document installation inline. `[verified]`
- Generated plugin packages are projected from canonical core directives; their READMEs mention this. `[verified]`

## Alternatives Considered

### Option A: Keep READMEs as-is and only fix what is broken

Rejected. Cross-package coherence is the goal: consumers and agents should find the same information in the same order in every published package, and ten divergent READMEs perpetuate the discoverability gap that motivated this standard.

### Option B: Generate READMEs from package metadata via the sync pipeline

Rejected. READMEs are curated prose carrying support boundaries, platform notes, and limitations that do not live in `package.json`; generating them would either strip that nuance or require embedding it in pipeline config. The task keeps READMEs hand-authored and structurally coherent, not identical.

### Option C: Auto-generate the changelog pages from package `CHANGELOG.md`

Rejected. Public changelog pages are curated, reader-facing summaries (for example the combined Pi/OMP page and the methodology changelog); auto-generation would import changeset boilerplate and per-version noise they deliberately avoid. They stay curated, and package `CHANGELOG.md` files are not edited.

### Option D: Retrofit all legacy internal documents to the new standard

Rejected as out of scope. The cost of rewriting historical ADRs and notes outweighs the benefit; the standard applies to new and materially revised documents, as recorded in `doc-format.md`.
